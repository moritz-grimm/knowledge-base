# ISO/IEC 25010 Software Quality

## Overview

ISO/IEC 25010 defines a **product quality model** for software and other ICT (information and communication technology) products. It splits the abstract term "quality" into nine **quality characteristics**, each divided further into **subcharacteristics**. The subcharacteristics are concrete enough to be specified as requirements for the product, measured and evaluated.

The model is used as a checklist and a shared vocabulary throughout the product lifecycle:

- Eliciting and formulating non-functional requirements, e.g. in the [requirement specification](./requirements-specification.md)
- Checking a set of requirements for gaps
- Deriving test objectives and acceptance criteria
- Evaluating and comparing finished products

The current edition is ISO/IEC 25010:2023. It belongs to the SQuaRE family (Systems and software Quality Requirements and Evaluation, ISO/IEC 25000 to 25099).

## Product Quality Model

| Characteristic                                    | Key question                                                            | Subcharacteristics                                                                                                                                     |
| ------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [Functional suitability](#functional-suitability) | Do the functions meet the needs and deliver correct results?            | Functional completeness, functional correctness, functional appropriateness                                                                            |
| [Performance efficiency](#performance-efficiency) | How fast does the product respond, and how many resources does it use?  | Time behaviour, resource utilization, capacity                                                                                                         |
| [Compatibility](#compatibility)                   | Does the product work together with other products?                     | Co-existence, interoperability                                                                                                                         |
| [Interaction capability](#interaction-capability) | Can the intended users operate the product?                             | Appropriateness recognizability, learnability, operability, user error protection, user engagement, inclusivity, user assistance, self-descriptiveness |
| [Reliability](#reliability)                       | Does the product work without failure over a period of time?            | Faultlessness, availability, fault tolerance, recoverability                                                                                           |
| [Security](#security)                             | Are data and functions protected against unauthorized access?           | Confidentiality, integrity, non-repudiation, accountability, authenticity, resistance                                                                  |
| [Maintainability](#maintainability)               | How easily can the product be changed?                                  | Modularity, reusability, analysability, modifiability, testability                                                                                     |
| [Flexibility](#flexibility)                       | Can the product be moved to other environments or scaled?               | Adaptability, scalability, installability, replaceability                                                                                              |
| [Safety](#safety)                                 | Does the product avoid endangering people, property or the environment? | Operational constraint, risk identification, fail safe, hazard warning, safe integration                                                               |

## Characteristics

### Functional Suitability

- **Functional completeness:** The functions cover all specified tasks and user objectives.
- **Functional correctness:** The functions deliver correct results with the required precision, e.g. a correctly calculated VAT amount.
- **Functional appropriateness:** The functions support the task without unnecessary steps. The criterion corresponds to suitability for the task in ISO 9241-110.

### Performance Efficiency

- **Time behaviour:** Response times and throughput rates meet the requirements, e.g. a search result within one second.
- **Resource utilization:** The product uses no more than the specified amount of CPU, memory, storage, network bandwidth or energy.
- **Capacity:** The product meets the maximum limits of a product parameter, e.g. the number of concurrent users, stored records or transactions per second.

### Compatibility

- **Co-existence:** The product performs its functions in a shared environment without impairing other products, e.g. two applications on the same server that do not compete for the same port.
- **Interoperability:** The product exchanges information with other products, and both sides can use the exchanged information, e.g. an export in a format that the accounting system imports.

### Interaction Capability

Interaction capability describes properties of the product itself that make interaction possible. The usability of the quality-in-use model (ISO/IEC 25019), by contrast, is evaluated on the result of real use: whether users reach their goals effectively, efficiently and satisfactorily in a real context of use. Good interaction capability makes this more likely but does not guarantee it, because the result also depends on the users, their tasks and the environment. An appointment booking app designed and tested for users familiar with smartphones can meet all interaction capability requirements. If it is later introduced in a retirement home, many residents still fail to book an appointment.

- **Appropriateness recognizability:** Users recognise from a first impression, a demonstration or the documentation whether the product suits their needs.
- **Learnability:** Specified users learn to use specified functions within a specified time.
- **Operability:** The product is easy to operate and control.
- **User error protection:** The product prevents operating errors, e.g. through input validation or a confirmation prompt before deleting.
- **User engagement:** The user interface presents functions and information in an inviting and motivating way.
- **Inclusivity:** People of different backgrounds, e.g. age, culture, language or gender, can use the product.
- **User assistance:** Users with the widest range of characteristics and capabilities, including people with disabilities, reach their goals, e.g. through screen reader support or adjustable font sizes.
- **Self-descriptiveness:** The product presents the information needed to use it where it is needed, so that its functions are obvious without consulting the documentation.

### Reliability

- **Faultlessness:** The product performs its functions without fault under normal operation.
- **Availability:** The product is operational and accessible when it is needed. Availability is usually specified as a percentage of uptime and agreed in an [SLA](../commercial/itsm/sla.md).
- **Fault tolerance:** The product works as intended despite hardware or software faults, e.g. a server that keeps running after a disk failure thanks to [RAID](../fundamentals/raid.md).
- **Recoverability:** After an interruption or a failure, the product recovers the affected data and re-establishes the desired state, e.g. through backups and a defined restart procedure.

### Security

Confidentiality, integrity and authenticity are explained in detail under [IT security goals](../fundamentals/security-goals.md).

- **Confidentiality:** Data is accessible only to authorized persons or systems.
- **Integrity:** Data and programs are protected against unauthorized modification or deletion by attacks or computer errors.
- **Non-repudiation:** Actions and events can be proven afterwards, so that they cannot be denied later, e.g. through digital signatures.
- **Accountability:** Actions can be traced uniquely to the entity that performed them, e.g. through audit logs.
- **Authenticity:** The identity of a user or a resource can be proven to be the one claimed.
- **Resistance:** The product keeps operating while under attack by a malicious actor.

### Maintainability

- **Modularity:** The product consists of components, so that a change to one component has minimal impact on the others.
- **Reusability:** A component can be used in more than one system or to build other components.
- **Analysability:** The impact of an intended change, the cause of a failure or the parts to be modified can be identified efficiently.
- **Modifiability:** The product can be changed without introducing defects or degrading its quality.
- **Testability:** Test criteria can be defined and tests performed efficiently, e.g. because functions can be tested in isolation by [unit tests](../fundamentals/unit-tests.md).

### Flexibility

- **Adaptability:** The product can be adapted to different or changing hardware, software or usage environments with little effort, e.g. another operating system or database system.
- **Scalability:** The product handles growing or shrinking workloads by adapting its capacity, e.g. by adding further server instances.
- **Installability:** The product can be installed and uninstalled successfully and with little effort in a specified environment.
- **Replaceability:** The product can replace another product for the same purpose in the same environment with little effort, e.g. a new CRM system that imports the customer data of the previous one and offers the same interfaces.

### Safety

Protecting the product itself against attacks belongs to [security](#security), not to safety.

- **Operational constraint:** The product restricts its operation to safe parameters or states when a hazard occurs.
- **Risk identification:** The product detects a course of events or operations that exposes people, property or the environment to an unacceptable risk.
- **Fail safe:** In case of a failure, the product switches automatically to a safe operating mode or returns to a safe state, e.g. a traffic light that switches to flashing amber.
- **Hazard warning:** The product warns of unacceptable risks, so that the users can react in time.
- **Safe integration:** The product stays safe during and after integration with other components.

## Changes Compared to ISO/IEC 25010:2011

The 2011 edition has eight characteristics. Characteristics and subcharacteristics not listed in the table are the same in both editions.

| ISO/IEC 25010:2011    | ISO/IEC 25010:2023         | Change                                                                                                                                               |
| --------------------- | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Usability             | Interaction capability     | Renamed; user interface aesthetics replaced by user engagement; accessibility split into inclusivity and user assistance; self-descriptiveness added |
| Portability           | Flexibility                | Renamed; scalability added, previously part of adaptability                                                                                          |
| Reliability: maturity | Reliability: faultlessness | Subcharacteristic renamed                                                                                                                            |
| Security              | Security                   | Resistance added                                                                                                                                     |
| None                  | Safety                     | New characteristic                                                                                                                                   |

The quality-in-use model, which describes the effect of a product on its users in a concrete context of use, was part of the 2011 edition and has moved to the separate standard ISO/IEC 25019.

## Predecessor ISO/IEC 9126

ISO/IEC 9126 was replaced by ISO/IEC 25010 in 2011. ISO/IEC 9126 defined six characteristics:

| ISO/IEC 9126    | ISO/IEC 25010:2023                                                                                                                        |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Functionality   | Functional suitability; the former subcharacteristics security and interoperability became the characteristics security and compatibility |
| Reliability     | Reliability                                                                                                                               |
| Usability       | Interaction capability                                                                                                                    |
| Efficiency      | Performance efficiency                                                                                                                    |
| Maintainability | Maintainability                                                                                                                           |
| Portability     | Flexibility                                                                                                                               |

## Worked Example: Classifying Quality Requirements

The following requirements come from the requirement specification of an online shop:

| #   | Requirement                                                                                  | Characteristic         | Subcharacteristic     |
| --- | -------------------------------------------------------------------------------------------- | ---------------------- | --------------------- |
| 1   | The product search returns results within one second for 95 % of all requests.               | Performance efficiency | Time behaviour        |
| 2   | The shop handles 5,000 concurrent users.                                                     | Performance efficiency | Capacity              |
| 3   | The shop is reachable 99.9 % of the time per month.                                          | Reliability            | Availability          |
| 4   | After a server failure, operation resumes within 30 minutes without losing completed orders. | Reliability            | Recoverability        |
| 5   | Every price change is logged with the user and a timestamp.                                  | Security               | Accountability        |
| 6   | Orders are transferred to the existing ERP system via a REST interface.                      | Compatibility          | Interoperability      |
| 7   | A new payment provider can be connected without changes to the order module.                 | Maintainability        | Modularity            |
| 8   | The checkout can be completed using only the keyboard and a screen reader.                   | Interaction capability | User assistance       |
| 9   | Before an order is placed, a summary page asks for confirmation.                             | Interaction capability | User error protection |
| 10  | The shop runs on both PostgreSQL and MariaDB.                                                | Flexibility            | Adaptability          |

What this example shows: each requirement can be assigned to exactly one subcharacteristic because it names a measurable value or a verifiable condition. A requirement such as "The shop must be fast" fits several subcharacteristics at once and cannot be accepted, see the [SMART criteria](./smart.md).

## Common Mistakes

1. **Safety and security treated as the same characteristic:** Security protects the data and functions of the product against unauthorized access and attacks. Safety protects people, property and the environment against harm caused by the product. A patient database that leaks records violates security, while an infusion pump that delivers the wrong dose violates safety.
2. **Availability assigned to security:** In ISO/IEC 25010, availability is a subcharacteristic of reliability. The mix-up stems from the CIA triad of the [IT security goals](../fundamentals/security-goals.md), in which availability is a security goal.
3. **Names of both editions mixed:** Usability and portability are the names of the 2011 edition. A requirements catalogue that combines them with interaction capability or safety leaves open which model the evaluation refers to.
4. **Performance efficiency reduced to speed:** Time behaviour is only one of three subcharacteristics. A system that responds quickly but needs ten times the planned memory, or fails beyond 100 concurrent users, does not meet performance efficiency either.
5. **Functional suitability confused with the functional requirements:** Functional requirements state what the product should do. Functional suitability evaluates how completely, correctly and appropriately the implemented functions meet those requirements.
6. **Quality requirement without a measurable value:** "The system must be user-friendly" can neither be tested nor accepted. "New employees complete an order without assistance after 15 minutes of training" can be tested and belongs to learnability.
