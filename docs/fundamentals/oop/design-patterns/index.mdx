# Design Patterns

## Overview

A design pattern is a named, proven template for solving a recurring design problem in object-oriented software. It is not finished code but a description of classes, their responsibilities and their collaboration, which is adapted to the concrete situation.

The term goes back to the book *Design Patterns: Elements of Reusable Object-Oriented Software* (1994) by Gamma, Helm, Johnson and Vlissides, known as the "Gang of Four" (GoF). It describes 23 patterns, each with a name, the problem it solves, the solution and its consequences.

Patterns provide a shared vocabulary: "the price display is an [observer](./observer.md) of the stock ticker" tells another developer that the ticker keeps a list of registered displays and notifies each of them on every price change, without describing that structure explicitly.

A design pattern solves a problem within one class or a few collaborating classes. Problems concerning the structure of an entire application are solved by architecture patterns such as MVC, layered architecture or microservices.

## Common Mistakes

1. **Pattern without a problem:** A [strategy](./strategy.md) interface with a single implementation or a [factory](./factory-method.md) that only ever creates one class adds classes and indirection without benefit.
