# ISO 9241-110 Interaction Principles

## Overview

ISO 9241-110 belongs to the ISO 9241 series "Ergonomics of human-system interaction". It defines seven **interaction principles** for the design and evaluation of interactive systems. The principles apply to every kind of user interface, from desktop applications and websites to apps and voice assistants.

The principles serve two purposes:

- Design guideline when user interfaces are drafted, e.g. as a [wireframe](./wireframe-mockup-prototype.md)
- Checklist when an existing user interface is evaluated and the causes of usability problems are searched for

The principles are the means, [usability](./usability.md) according to ISO 9241-11 is the goal. Whether a user interface is usable is measured by effectiveness, efficiency and satisfaction. The principles explain why a user interface may miss that goal and what to change.

The current edition is ISO 9241-110:2020, see [Changes Compared to the 2006 Edition](#changes-compared-to-the-2006-edition).

## The Seven Principles

| Principle                                                               | Key question                                                                        |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| [Suitability for the user's tasks](#suitability-for-the-users-tasks)    | Does the system support the task without unnecessary steps, fields or detours?      |
| [Self-descriptiveness](#self-descriptiveness)                           | Is it clear at all times where the user is, what can be done and what is happening? |
| [Conformity with user expectations](#conformity-with-user-expectations) | Does the system behave consistently and as users know it from other systems?        |
| [Learnability](#learnability)                                           | Does the system help users to learn how to use it?                                  |
| [Controllability](#controllability)                                     | Do users determine pace, order and direction of the interaction themselves?         |
| [Use error robustness](#use-error-robustness)                           | Are errors prevented, and can errors that occur be corrected with little effort?    |
| [User engagement](#user-engagement)                                     | Is the system trustworthy and pleasant enough to be used willingly?                 |

## Principles in Detail

### Suitability for the User's Tasks

The system offers exactly what the task requires. Default values, sensible preselections and the automatic filling of known data reduce the effort.

- **Fulfilled:** An order form shows only the fields needed for an order and prefills the delivery address from the customer account.
- **Violated:** A form asks for a fax number and a second address although neither is needed for the task.

### Self-descriptiveness

The user interface itself shows the current state, the available actions and the result of every action, so users need neither documentation nor guesswork to find their way.

- **Fulfilled:** After an order is sent, the message "Order sent to supplier Meier" appears. A progress indicator shows "Step 2 of 3".
- **Violated:** After a click on "Book", nothing visible happens, and users cannot tell whether the booking was saved.

### Conformity with User Expectations

The system behaves consistently within itself and follows the conventions users know from other systems: the same terms, the same arrangement, the usual controls for the usual inputs.

- **Fulfilled:** A date is selected with a date picker, the primary button is placed where it sits in comparable applications, and "Save" means the same in every dialogue.
- **Violated:** A date must be typed in a free text field without an indication of the expected format.

### Learnability

The system supports users while they learn to use it: it guides them through first steps, offers hints and makes relationships between functions visible.

- **Fulfilled:** On first launch, a short hint explains how a demand is recorded. Tooltips explain rarely used functions.
- **Violated:** A function is reachable only through an undocumented keyboard shortcut.

### Controllability

Users start the interaction and determine its pace, order and direction. An interaction can be interrupted, continued later, reversed or cancelled.

- **Fulfilled:** A multi-step booking can be cancelled at any time and allows going back step by step without losing entered data.
- **Violated:** A wizard offers neither "Back" nor "Cancel", and a timeout discards the input after two minutes.

### Use Error Robustness

The system prevents errors where possible, makes errors that occur easy to recognise and correct, and limits their consequences.

The principle has three levels:

1. **Prevention:** Controls that admit only valid input, e.g. a date picker instead of a free text field, or a confirmation prompt before deleting
2. **Recognition:** An error message that states what is wrong and how to correct it, placed next to the affected field
3. **Recovery:** Correction with little effort, e.g. the form keeps all valid input, or an undo function reverses the last action

- **Fulfilled:** If the quantity is missing, the field is highlighted and the message "Please enter a quantity" appears next to it.
- **Violated:** Invalid input only produces "Error 0x8" without an explanation of what to do.

### User Engagement

The system presents its functions and information in an inviting and motivating way and earns the users' trust, so that they use it willingly and continue to use it.

- **Fulfilled:** The app responds smoothly, looks tidy and states transparently what happens to the entered data.
- **Violated:** A booking page looks outdated and gives no confirmation, so that patients prefer to call the practice.

## Changes Compared to the 2006 Edition

The 2006 edition was titled "Dialogue principles", and its names are still in widespread use.

| ISO 9241-110:2006                 | ISO 9241-110:2020                 | Change                                                 |
| --------------------------------- | --------------------------------- | ------------------------------------------------------ |
| Suitability for the task          | Suitability for the user's tasks  | Renamed                                                |
| Self-descriptiveness              | Self-descriptiveness              | Unchanged                                              |
| Conformity with user expectations | Conformity with user expectations | Unchanged                                              |
| Suitability for learning          | Learnability                      | Renamed                                                |
| Controllability                   | Controllability                   | Includes suitability for individualization             |
| Error tolerance                   | Use error robustness              | Renamed; prevention of errors emphasised more strongly |
| Suitability for individualization | None                              | Integrated into controllability                        |
| None                              | User engagement                   | New principle                                          |

## Related Models

- **ISO/IEC 25010:** The quality characteristic [interaction capability](../../projectmanagement/iso-25010.md#interaction-capability) describes the operation-related properties of a software product as quality requirements. Several subcharacteristics correspond to interaction principles, e.g. learnability, user error protection and self-descriptiveness.
- **Nielsen's heuristics:** The ten usability heuristics by Jakob Nielsen (1994) are a checklist for expert evaluations that is widespread in practice. They cover largely the same ground as the interaction principles, e.g. "visibility of system status" corresponds to self-descriptiveness and "error prevention" to use error robustness.

## Worked Example: Evaluating an Appointment Booking Form

A medical practice offers online appointment booking. Patients complain that the booking is confusing and error-prone, and that they never know whether the appointment was booked. The booking screen shows "Step 2 of 3" and contains twelve input fields: salutation, first name, last name, date of birth, street, postcode and city, second address, phone, fax, email, a free text field "Date (please type)" and a field for the reason for the visit. Below the fields there is a single button "Book appointment".

| Observation                                                                         | Violated principle                | Improvement                                                                                               |
| ----------------------------------------------------------------------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------- |
| After a click on "Book appointment", no message appears.                            | Self-descriptiveness              | Show a confirmation page with date, time and doctor, and send a confirmation email.                       |
| The date has to be typed as free text, e.g. "3.10.", and no date picker is offered. | Conformity with user expectations | Replace the text field with a date picker that shows only free slots.                                     |
| Invalid input only produces "Invalid" in red without an explanation.                | Use error robustness              | State the cause and the expected format next to the field, e.g. "Please select a date from the calendar". |
| Fax and second address are requested although they are not needed for a booking.    | Suitability for the user's tasks  | Remove fax and second address; reduce the form to the data the practice needs.                            |
| It is not possible to go back a step or cancel the booking.                         | Controllability                   | Add "Back" and "Cancel" buttons; keep entered data when going back.                                       |

What this example shows: one improvement often addresses several principles. The date picker fixes the expectation problem and prevents the invalid input at the same time. Every improvement names a concrete change to the user interface, so that it can be implemented and checked directly.

## Common Mistakes

1. **Self-descriptiveness confused with conformity with user expectations:** Self-descriptiveness is about whether the user interface explains itself, e.g. through labels, status and feedback. Conformity with user expectations is about whether it behaves consistently and according to familiar conventions. A missing confirmation after sending violates self-descriptiveness, a free text field for a date violates conformity with user expectations.
2. **Improvement without a concrete measure:** "Make the form more user-friendly" or "improve the error message" cannot be implemented as stated. "Show the message 'Please enter the date as DD.MM.YYYY' below the date field" can be implemented and checked.
3. **Use error robustness reduced to error messages:** An error message helps only after the error has occurred. The principle also covers preventing errors, e.g. with controls that admit only valid input, and correcting them with little effort, e.g. by keeping all valid input.
4. **Controllability reduced to a cancel button:** A cancel button only lets users abandon the interaction and lose their input. Controllability also covers going back, interrupting and resuming an interaction, and determining the pace.
5. **User engagement taken as the successor of suitability for individualization:** Suitability for individualization was integrated into controllability. User engagement is a new principle about trust and motivation and has no predecessor in the 2006 edition.
6. **Principles fulfilled taken as proof of usability:** The principles are a design and inspection aid. Whether real users reach their goals effectively, efficiently and satisfactorily is shown only by an evaluation with users, see [usability](./usability.md#usability-testing).
